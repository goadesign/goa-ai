# v0.89.0 — Provider-owned agent operations, release-safe continuations, and Goa v3.35.0

Goa-AI's `codegen`, `runtime`, `registry`, `mcp`, and `features/model/bedrock`
packages generate typed agent and MCP contracts from Goa designs, execute durable
agent workflows and distributed registry tool calls, and connect planners to model
providers. This release upgrades Goa-AI to **Goa v3.35.0** and **Go 1.27.3**,
shrinks generated tool-codec packages by scoping forced types to their owning
service, preserves accepted tool history and worker routing across provider
releases, adds provider-owned Agent operations and single-operation paginated
tools, and preserves caller workflow metadata across continuations.

This is a **breaking upgrade** after v0.88.0. Regenerate contracts with Goa
v3.35.0 and deploy updated registry replicas, providers, consumers, and runtime
workers together.

## Scope generated tool types and shard large codec files

The `codegen/agent` and `codegen/mcp` packages generate JSON codecs, validators,
and OpenAPI/JSON schemas for agent toolsets and MCP servers.

Previously, `goa gen` forced every user type referenced anywhere in the root design
into every generated service's `service.go` and emitted a single monolithic
`codecs.go` / `types.go` / `validate.go` file per toolset. In multi-service
repositories with shared domain types, every service received hundreds of
thousands of lines of unused types and helpers, slowing down both `goa gen` and
`go build`.

Now, `goa-ai` scopes forced tool payload, result, and server-data types to the
service that owns each toolset and shards generated JSON codec files into
bounded, deterministic sibling files (`codecs.go`, `codecs_2.go`, ...) whenever a
file exceeds the line budget. Multi-service repositories generate and compile
substantially faster with smaller packages.

## Preserve accepted history, paging, and worker routing across releases

The `runtime/agent/runtime`, `runtime/agent/engine/temporal`, and `registry`
packages coordinate long-running agent runs, paginated tool queries, and
continuation workflows when a tool pauses for user input or durable job
completion.

Previously, deploying a new tool schema or worker release while a run was paused
or paging through results could reject historical tool observations, lose the
accepted root workflow target during cancellation or answer delivery, or re-parse
unchanged registry tool definitions on every turn.

Now:

- **Accepted root workflow targets survive releases:** When a run is accepted,
  the runtime records the exact workflow name and task queue in the saved start
  recipe. Subsequent answers (`StartToolContinuation`) and cancellations target
  the accepted worker rather than guessing from the current process registration
  (#481).
- **Continuation workflows preserve caller `Memo`:** `StartToolContinuation` and
  `EnsureToolContinuationCompletion` accept a final `memo map[string]any`
  argument so successor workflows retain caller-supplied engine metadata. The
  runtime saves the encoded Memo before submitting the workflow and rejects
  conflicting retries with `storage.ErrSeedConflict` (#482).
- **Historical observations and completed paging survive tool changes:** Saved
  tool results and completed paging chains remain readable after a provider
  updates a tool's input schema or pagination contract, while new pages route to
  current providers (#456, #457, #461, #463, #472, #481).
- **Single-operation paginated tools:** Paginated tools publish as one catalog
  operation with object-rooted JSON schemas (`$schema` and `$defs` at the
  document root) and branch-matched paging hints (#462, #464, #470, #471, #473).
- **Cached registry schema compilation:** Unchanged registry tool declarations
  and identical input schemas are compiled once instead of being reparsed and
  copied on every turn (#467, #469, #474, #479).

## Provider-owned Agent operations and static registry bindings

The `runtime/agent/runtime` and `registry` packages allow one agent to invoke
another agent as a tool, either through a compiled Go registration or through
the tool registry.

Previously, registry-backed agent tools could not expose provider-owned durable
operations with revision-pinned configurations, and generated native agent tools
could not bind to a selected registry declaration while keeping their compiled
local worker and prompt configuration. Resolver outputs also passed raw message
slices (`AgentToolConfiguration.Messages`), which could not distinguish an
intentionally empty transcript from an uninitialized configuration.

Now:

- **Provider-owned Agent operations:** Registry wire protocol **15** supports
  provider-owned Agent operations, revision-owned Agent operation contracts,
  timeout policy preservation, and read-only inspection of saved catalog
  registrations (#430, #440, #446, #448, #481).
- **Static native Agent bindings:** Generated native Agent tools can bind to
  selected registry registrations while preserving their executable tool
  selection and compiled worker route (#437, #439, #442, #444, #451).
- **Explicit `AgentHistory` on resolvers:** `AgentToolConfiguration.Messages` is
  replaced by required `History` constructed via
  `runtime.LiteralAgentHistory(messages)` (#430).

Before:

```go
return &runtime.AgentToolConfiguration{
    Messages: messages,
}, nil
```

After:

```go
return &runtime.AgentToolConfiguration{
    History: runtime.LiteralAgentHistory(messages),
}, nil
```

## MCP protocol clients, runtime-defined tools, and Bedrock structured output

The `mcp`, `runtime/mcp`, and `features/model/bedrock` packages connect MCP
clients and servers and invoke Amazon Bedrock models.

- **Runtime-defined MCP tools and basic HTTP clients:** MCP code generation
  supports contracts for runtime-defined tools (#432), wraps dynamic results for
  basic MCP `2025-11-25` HTTP clients (#434), and keeps silent HTTP responses
  active after middleware (#459).
- **Text-only exact operation calls:** Text-only runs can invoke exact registry
  and MCP operations without interactive UI capabilities (#445, #460).
- **Unary structured output on Bedrock Responses:** The Bedrock Responses client
  supports unary structured JSON output alongside streaming responses (#452) and
  avoids overload retries for events already held by a provider (#468).
- **Go 1.27.3 and Goa v3.35.0 baseline:** All modules require **Go 1.27.3** and
  **Goa v3.35.0**, pulling in Go 1.27.3's emergency `crypto/x509` intermediate
  CA blocklist (`CVE-2026-111943`), Go 1.27.2's 15 HTTP/2, HTTP/1, TLS, and MIME
  security fixes, and Goa v3.35.0's 6.5x faster `goa gen` pipeline (#480).

## Required upgrade actions

1. **Install Go 1.27.3+ and regenerate with Goa v3.35.0.** Update your module's
   `go` directive to `1.27.3`, upgrade `goa.design/goa/v3` to `v3.35.0` and
   `goa.design/goa-ai` to `v0.89.0`, and run `goa gen` across all design
   packages.
2. **Update `StartToolContinuation` and `EnsureToolContinuationCompletion`
   callers.** Add the final `memo map[string]any` argument (pass `nil` when no
   workflow Memo is attached):
   ```go
   handle, err := rt.StartToolContinuation(ctx, req, nil)
   res, err := rt.EnsureToolContinuationCompletion(ctx, req, nil)
   ```
3. **Update `AgentToolResolver` implementations.** Replace
   `Messages: messages` on `runtime.AgentToolConfiguration` with
   `History: runtime.LiteralAgentHistory(messages)` (use
   `runtime.LiteralAgentHistory(nil)` for an intentionally empty transcript).
4. **Coordinate registry wire protocol 15 and suspension checkpoint v14.**
   Deploy regenerated registry replicas, providers, consumers, and runtime
   workers together. Current suspension checkpoints use
   `goa-ai.run-suspension.v14` and registry wire protocol **15**; drain or
   settle incompatible in-flight calls before replacing workers. See the
   [stored-work cutover](../runtime.md#executable-ownership-and-upgrade) and
   [registry storage upgrade](../runtime.md#registry-storage-upgrade).
